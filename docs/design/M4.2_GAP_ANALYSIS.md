# M4.2 — Product Workflow Refactor: GAP ANALYSIS

> **Status:** Analysis complete → refactor in progress.
> **Scope reviewed:** entire `/ai` knowledge base (00–08, MATCHING_ENGINE, OFFLINE_STRATEGY),
> all ADRs (0001–0016), all milestones, the backend (Domain/Application/Api/Infrastructure),
> the Angular admin (`admin/src/app`), and the Flutter mobile app (`mobile/lib`).
> **Method:** read the source; did **not** assume the current implementation is correct.

The mission (Business Bible §1–2): a **two-sided marketplace** that fills a truck's empty
return leg with a shipper's load. Every finding below is judged against *that* — not against
"is it a working CRUD screen."

---

## 0. Executive summary — the three root causes

Almost every symptom traces to three missing seams:

1. **No role is ever assigned.** Registration creates an account with **zero roles**; only the
   4 seeded demo users have roles. The 9-role RBAC catalogue and policy map are well-built but
   **nothing feeds them**. → role-based registration, role-gated navigation, and "drivers can't
   post / load owners can't approve" are all *un-enforceable today* for real users.
2. **No location intelligence.** Loads carry caller-supplied raw lat/lng + a free-text address;
   the mobile app **hardcodes Chennai→Coimbatore coordinates regardless of typed text**. There is
   no geocoding/autocomplete, no distance, no ETA, and no `IRouteService`/`ILocationSearchService`
   abstraction. → the core marketplace datum (where, how far) is fiction.
3. **No matching.** `loads/available` returns **every** posted load to **every** authenticated
   user. None of `MATCHING_ENGINE.md`'s 8 hard filters exist. → the product's single most
   valuable module (Project Rules §4) is absent; the app is a shared bulletin board, not a
   marketplace.

Everything else is a consequence or a cosmetic layer on top of these.

## 1. Incorrect workflows

| # | Workflow | What it does today | Why it's wrong | Fix milestone |
|---|----------|--------------------|----------------|---------------|
| W1 | **Registration** | `POST auth/register` (email/password/phone) → account `Active`, **no role, no profile** | Role-based registration (Business Bible §3, T&S §7) is impossible; every downstream gate silently fails | A |
| W2 | **Post Load** | Reachable from the **driver** home tab; sends **hardcoded** Chennai→Coimbatore coords | Drivers must never see "Post Load" (explicit); coordinates are fabricated | A, C, E |
| W3 | **Browse / match** | `BrowseAvailableAsync` returns all `Posted` loads to anyone | Violates "drivers only see compatible loads" and T&S §1 "no unverified party transacts" | D |
| W4 | **Accept load** | `AcceptAsync(loadId)` flips `Matched→Booked` with no driver, vehicle, or verification | No assignment, no Booking/Trip link, no T&S gate; a wrong/unverified truck can "accept" | D, F |
| W5 | **Document upload (mobile)** | GETs all drivers, uses `list.first['id']` as "my" driver | Attaches KYC docs to **whatever driver is first in the list**, not the signed-in user — a correctness *and* privacy defect | A, B |
| W6 | **Trips (admin & mobile)** | No "my trips"/list endpoint; user **pastes a GUID** | Not a usable operator or driver workflow | F |
| W7 | **Driver onboarding** | `drivers/register` allowed for any authenticated user; grants no `Driver` role | Onboarding is decoupled from identity/role; anyone can create a driver profile | A, B |

## 2. Unnecessary / misplaced screens & actions

- **Mobile "Post Load"** on the driver home tab — remove from the driver app entirely (W2).
- **Mobile Map tab/screen** with hardcoded Chennai/Coimbatore markers — keep the widget but drive
  it from **real load/trip coordinates**; a static two-pin map is decorative.
- **Admin: all 4 trip-transition buttons always shown** regardless of current state — should reflect
  the trip's actual state machine.
- **Admin "Verified & ready" stat** is a duplicate of the active-driver count, mislabeled.
- **Duplicate Settings** (mobile Settings screen + Profile menu items) — consolidate.
- **Mobile Vehicle screen** is a pure static placeholder ("Not linked yet") — either wire it to a
  real per-driver vehicle endpoint or hide it until M5.

## 3. Missing workflows

- **Choose Account Type** first screen (Driver vs Load Owner) — does not exist.
- **Role-specific registration** (driver KYC fields incl. licence + photo + "vehicle owner?" branch;
  load-owner company/GST/contact) — does not exist; one generic form only.
- **Vehicle registration with documents** (RC/insurance/fitness/permit) as a driver flow — partial:
  a vehicle *service* exists (carrier-scoped), but there is no driver-facing "add my vehicle + upload
  its papers" flow, and documents attach by the W5 hack.
- **Location autocomplete + auto distance/ETA** — does not exist (root cause #2).
- **Compatible-loads matching** — does not exist (root cause #3).
- **Admin verification queues** for *pending load owners* and *pending vehicles* — admin only has a
  driver list and a pending-documents list; no load-owner or vehicle approval queue.
- **"My trips" / "my loads"** list endpoints for both clients — missing.
- **Document expiry reminders / auto-EXPIRED transition** (T&S §6) — not implemented.
- **Notifications delivery** — mobile shows 4 hardcoded fake items; no backend.

## 5. Duplicate features

- **Two "register driver" surfaces** with different shapes: mobile `DriverProfileScreen` (fullName/
  mobile/licence, `carrierId=null`) vs the intended KYC flow. Consolidate into the role-based
  registration + a driver profile step.
- **Enum→label maps duplicated** in `admin/core/api/enums.ts` and `mobile/lib/core/enums.dart` —
  acceptable (documented mirrors) but will silently drift; note as a risk.
- **Settings duplicated** (see §2).

## 6. Business mistakes (marketplace-logic errors)

- **B1 — Anyone can transact.** No verification gate on accept/post beyond the (unassigned) Shipper
  policy. Directly violates T&S §1. **Highest-severity business defect.**
- **B2 — Fabricated geography.** Hardcoded coordinates mean distance/ETA/matching would all be
  computed on fiction. The north-star metric (deadhead km eliminated, Business Bible §7) is
  unmeasurable.
- **B3 — Role-less accounts.** A marketplace with no notion of "which side are you" cannot route
  workflows, notifications, or trust correctly.
- **B4 — No commission record on completion.** ADR-0005 says the platform *records commission owed*;
  no such record is created on a completed booking. (Deferred but must be designed-for.)

## 7. UX problems

- Single-persona "driver" branding while mixing shipper + onboarding flows → confusing for both sides.
- Dead back-navigation to a non-existent `/dashboard` route (mobile PostLoad & DriverProfile screens).
- Trips require pasting a GUID (admin **and** mobile) — unusable.
- Hardcoded "Verified"/"4.8"/"₹0"/"0 trips" give false status signals.
- No pending/verification status surfaced to the user after registration.
- Reject-document reason is hardcoded `'Rejected from console'` (admin) — no operator input.

## 8. Security concerns

- **S1 — Cross-user document attachment** (W5): a driver's uploaded KYC can bind to another driver's
  profile. Confidentiality + integrity defect. **Fix in Milestone A/B** (server resolves the driver
  from the JWT, never a client-supplied/"first" id).
- **S2 — No client-side authZ, only reactive 403s.** Acceptable for security (server enforces) but the
  clients must still gate UI by role for correctness and UX.
- **S3 — Envelope `success:false` ignored by admin ApiService** — a 200 error body is treated as
  success. Harden the unwrap.
- **S4 — `usesCleartextTraffic=true`** in the mobile release manifest (dev LAN http). Acceptable for
  dev; must be removed for production (already commented).
- **S5 — Registration grants role from client input** (once we add it): must whitelist to
  {Driver, LoadOwner/Shipper} only — never allow self-granting internal/admin roles.

## 9. Scalability concerns

- **Geo without PostGIS.** `GeoCoordinate` is stored as plain columns; corridor/radius matching needs
  **PostGIS geometry + spatial index** (ADR-0015 flagged this deferral). Matching on non-indexed
  lat/lng will not scale. Milestone C/D introduces the seam; PostGIS geometry is a follow-up.
- **No caching / background jobs.** Expiry reminders, matching recomputation, and notification fan-out
  need a scheduler + cache (Redis TBD, Tech Bible §11) — not yet chosen.
- **List endpoints unpaginated in services** (return `IReadOnlyList`), client-side pagination only.
  Fine at seed scale; must move to server-side `PagedResult` before real volume.
- **External route provider rate limits.** Nominatim/OSRM public endpoints are rate-limited; the
  abstraction must allow a self-hosted/Google swap without business changes (per the user's mandate).

## 10. What is already good (keep)

- Clean Architecture boundaries, `Result`/envelope contract, M1.5 hardening, policy-based authZ seam.
- The **domain model is solid**: `DriverProfile` (Pending→Active, `IsTransactable`), `Vehicle`
  (Draft→Active gated on docs), `Load` lifecycle, `VehicleType`/`CargoType`, geo/`Distance` VOs.
  The refactor is overwhelmingly in the **application/API/client layers**, not the domain.
- ADR-0013's separation of **authentication vs trust-verification** is exactly right — we build on it.

## 11. Resolved ambiguities (inferred, not blocked — logged for ADR-0017)

1. **Login while Pending?** → **Yes.** A user logs in immediately after registration (to track status
   and upload documents) but is **not transactable** until an admin verifies. Auth ≠ trust (ADR-0013);
   T&S gates *transacting*, not *login*. Account status starts `Active` for auth; a separate
   verification status governs transactability.
2. **Role vs approval.** → Registration **grants the role** (so the client knows which side you are)
   and sets the profile to **pending verification**. Role = identity; verification = permission to
   transact.
3. **"Load Owner" vs "Shipper".** → Same actor. Keep the **domain/JWT role name `Shipper`** (stable
   claim, ADR-0013); **label it "Load Owner" in the UI**. No breaking role rename.
4. **Transport Company (optional).** → Not a separate MVP registration. The driver "**Vehicle owner?
   YES**" branch makes the driver an **owner-operator carrier** (creates a `Carrier` + `Association`
   under the hood). Fleet/Dispatcher UIs stay scaffolded for a later phase.
5. **Self-granted roles.** → Registration accepts only `Driver` or `LoadOwner`; the server maps
   `LoadOwner→Shipper` and **rejects any attempt to self-assign internal/admin roles** (S5).
